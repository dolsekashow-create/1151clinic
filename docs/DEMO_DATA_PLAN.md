## 1. أثر قرار RQ-02 على المخطط

### 1.1 هل كان التصميم الحالي كافيًا؟ **لا**

التصميم السابق:

```
appointments.provider_id → profiles(id) → auth.users(id)
```

أي أن **كل طبيب كان ملزَمًا بحساب مصادقة**. هذا يخالف القرار مخالفة مباشرة، ويُنتج
حسابات وهمية لأطباء لا يستخدمون النظام — **وهي حسابات قابلة لتسجيل الدخول فعليًا**،
أي سطح هجوم بلا أي مقابل وظيفي.

**الخلاصة: القرار غير قابل للتنفيذ بالتصميم الحالي.**

### 1.2 الترحيل المُقترح (أُنشئ ولم يُطبَّق)

📄 `supabase/migrations/20260817080000_service_providers.sql`

| # | التغيير | النوع |
|---|---------|-------|
| 1 | جدول `service_providers` — كيان تشغيلي مع `profile_id` **اختياري** (`unique`, `on delete set null`) | إنشاء |
| 2 | جدول `provider_branches` — يعكس نمط `branch_services` القائم؛ يمثّل «طبيب يعمل في الفروع أ وج لا ب» | إنشاء |
| 3 | `appointments.provider_id` → يشير إلى `service_providers` بدل `profiles` | **تبديل مفتاح أجنبي** |
| 4 | إعادة تعريف `app.guard_profile_sensitive_fields()` (كانت تشير للعمود المحذوف) | تعديل دالة |
| 5 | `profiles.is_service_provider` → **حذف عمود** | ⚠️ **DROP COLUMN** |
| 6 | سياسات RLS للجدولين + محفّزات التدقيق | إنشاء |

**اتجاه العلاقة مقصود:** المقدّم يشير إلى الحساب، لا العكس. فالطبيب يوجد أولًا، والحساب إضافة اختيارية.

**لماذا لا مفتاح مركّب `(provider_id, branch_id)`؟** لأن المقدّم قد يكون على مستوى
المنشأة ويخدم عدة فروع؛ فرض التطابق كان سيمنع الطبيب الزائر.

### 1.3 البند الوحيد الذي يحتاج قرارك: حذف العمود

`profiles.is_service_provider` صار **مصدر حقيقة ثانيًا** لنفس المعلومة بعد وجود
`service_providers.profile_id`. تفرّع المصدرين هو بالضبط نوع الخطأ الذي يُنتج
بيانات متناقضة بصمت.

| الخيار | النتيجة |
|--------|---------|
| **حذفه** (المقترح) | مصدر حقيقة واحد · **صفر فقدان بيانات — الجدول فارغ** |
| الإبقاء عليه | يبقى عمودًا مهجورًا مضلِّلًا · بقية الترحيلة تعمل بحذف هذا الجزء |

### 1.4 صلاحيات جديدة

ومُنحت لـ`branch_manager` و`reception` و`employee` (عرض) — لأن بناء الحجز يحتاج رؤية المقدّمين.

### 4.3 الحالات الحدّية

| السيناريو | المتوقع |
|-----------|---------|
| دخول الموظف الموقوف | الدخول ينجح · **كل الشاشات فارغة** |
| تعديل حركة مالية `posted` | مرفوض من المحفّز حتى لمالك `finance.approve` |
| تعديل/حذف حركة مخزون | مرفوض — دفتر append-only |
| فتح وردية ثانية لنفس المستخدم والخزينة | مرفوض — فهرس فريد جزئي |
| إنشاء خدمة مشتركة بحساب موظف فرع | **مرفوض** — الكتابة بنطاق فرع صارم |

### 4.4 الاختبار الحاسم — تجاوز الواجهة

استدعاء PostgREST مباشرةً بمفتاح Publishable وجلسة مدير فرع العليا، وطلب عميل جدة
**بالمعرّف صراحةً** → **يجب أن يعود فارغًا**. هذا وحده يُثبت أن الحماية في المحرّك
لا في الشاشة. سأجهّز سكربت تحقق آلي يشغّل كل حالات §4 بعد البذر.

## 5. النظام المالي: ما يعمل وما هو معلّق

### 5.1 قابل للتجربة ✅

تسجيل الحركات (إيراد/مصروف/دفعة مورد/تسوية/تحويل) · دورة `draft→posted→void` ·
**رفض تعديل المُرحَّل حتى لمالك `finance.approve`** · منع الحذف · دفاتر append-only ·
بنود القيد بمفتاح مركّب آمن للفرع · فتح الورديات ومنع المزدوجة · العهدة ·
المصروفات ومدفوعات الموردين · فصل الصلاحيات المالية · العزل الكامل · `idempotency_key`.

### 5.2 معلّق — `BUSINESS_RULE_PENDING` ⛔

| # | البند | الحالة الفعلية |
|---|-------|----------------|
| **P-01** | معادلة تقفيل الوردية | الأعمدة **تبقى NULL** · الإغلاق يسجّل الوقت والمسؤول فقط |
| **P-02** | دليل الحسابات وطريقة القيد | `account_ref` نص وصفي · **لا يُفرض توازن مدين = دائن** |
| **P-03** | الترحيل التلقائي من العمليات | **لا محفّز** · `source_module` مُعبَّأ للتتبع فقط |
| **P-04** | سير عمل العهدة | `status` مرن بلا موافقات |
| **P-06** | تقييم تكلفة المخزون | `unit_cost` مخزّن · لا متوسط ولا FIFO |
| **P-18** | التقارير المالية | `ReportRegistry` فارغ عمدًا |

**بوضوح:** ستسجّل حركات مالية محمية ومعزولة وغير قابلة للتعديل. **لن** تقفل وردية
بحساب حقيقي، ولا ترى ميزانًا، ولا يتولد قيد تلقائيًا من عملية مخزنية.
